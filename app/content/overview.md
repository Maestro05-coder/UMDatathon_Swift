## What this is

A single synthetic SWIFT-like payments file — **10,000,000 rows, ~4.95 GB** — was
generated by a hidden rule set. Our job was to reverse-engineer those rules and
prove each one against the file itself. Every finding below was measured on the
**full 10M rows** (DuckDB over parquet caches of the CSV) — every number quoted in
this app is exact, not a sample statistic. Random sampling was used only to shape
chart curves; rare buckets were always counted exactly.

<div class="verdict">The one sentence version: under every column sits a small
generator rule, and almost every rule shows itself as a number that is far away
from the number chance would produce.</div>

## The file in one view

| fact | value |
| :--- | :---- |
| rows | 10,000,000 (7,006 of them carry an anomaly label — 0.07%) |
| time window | 2023-04-30 → 2023-07-30 (90 days), epoch seconds, UTC |
| currencies | 155 (EUR 32.0%, USD 17.0%, GBP 8.7%, CHF 8.0% …) |
| country codes | 229 (182 with ≥1,000 rows) |
| banks | 8,727 distinct · 25,815,715 visible appearances |
| corridors | 24,017 sender→beneficiary country pairs |

## The columns everything is built from

| column | what it is |
| :--- | :--------- |
| `BIC8_PATH` | the route: `;`-separated bank ids. First bank = sender's bank, last = beneficiary's bank. `...` = one or more **hidden banks** we aren't shown |
| `ORDERING_BIC8` / `BENEFICIARY_BIC8` | stated sender/receiver bank — about 5% wrong, so the path is preferred |
| `EPOCH_SECONDS` | when the payment happened (UTC) |
| `CURRENCY_CODE` | the currency label on the payment |
| `USD_AMOUNT` | the amount, in USD terms |
| `CURRENCY_CONVERSION_COUNT` | how often neighbouring banks in the route use different currencies |
| `TOTAL_DURATION` | how long the payment took (seconds) |
| `TRANSACTION_TYPE_CODE` | Direct (2 banks) / Indirect / Covered (3+ banks) |
| `PARTICIPANT_COUNT` | number of banks shown in the path |
| `CONTINUITY_QFLAG` | QFLAG — "Y" if the path is fully shown, "N" if it contains `...` |
| `ORDERING_ACCOUNT` / `BENEFICIARY_ACCOUNT` | account strings (all `_FAKE_` placeholders) |
| `ORDERING_DETAILS` / `BENEFICIARY_DETAILS` | party profile text (name/address) |
| `ORDERING_TOKENS` / `BENEFICIARY_TOKENS` | the generator's template of the details |
| `ORDERING_TYPE` / `BENEFICIARY_TYPE` | B = business, C = person |
| `ANOMALY_TYPE` | anomaly label, or empty for a clean row |

## The method, in four moves

1. **Pick the column that should cause the effect** (sender bank, currency, country, route, label) — not "do anomalous rows look weird".
2. **Group all 10M rows by it** with DuckDB and measure the suspected mechanism directly.
3. **Compare against the chance baseline** — the number you'd get if nothing were going on (19% currency match, ~1% round numbers, 82% first contact …). A real rule lands far from its baseline. If it doesn't, we write the dead end down anyway.
4. **Hold everything else fixed** (same corridor, same bank, same country) before believing a number — and report the clean baseline next to every anomaly number.

Every group page below follows the same shape: the columns it uses, the rules and
how each was squeezed out, dead ends included, then the charts, then the full
write-up with proof rows straight from the file.

## Words the whole app uses

- **BIC8** — the 8-character bank id (e.g. `0309CHZ0`). Its characters 5–6 are the
  bank's country code.
- **clean row** — `ANOMALY_TYPE` is empty. Anomalies live in g8 only.
- **corridor** — sender country → beneficiary country pair.
- **hop / step / link** — one bank-to-bank leg of the route (per-group pages define
  their own flavour precisely).
- **hidden bank** — the `...` in a path: a bank that exists but is not shown.
- **dex** — "order of magnitude shift" on a log scale: +0.1 dex ≈ ×1.26,
  +1 dex = ×10. Used because amounts span billions.
- **median** — the typical value. Used instead of means because a single $1.39B
  payment would otherwise run the show.
